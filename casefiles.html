Teaching AI to be checkable

CASE-01 · GENAI DELIVERY WORKFLOWS
Context

Across several US client accounts, I brought Generative AI into my everyday delivery: list building, data cleaning, and persona classification run through Claude, ChatGPT, and Gemini. The work went faster at once; the open question was whether it could be trusted under deadline.

Problem

Faster is worthless if it is wrong. Early prompts were improvised per task, so results varied from run to run, and there was no checkpoint between an AI-generated output and a client deliverable. The risk was quiet: a plausible-looking but incorrect result slipping through unnoticed.

Approach

I framed it as two separate problems. Consistency is an input problem: fix it by standardising the prompts. Correctness is an output problem: fix it with a checkpoint before deployment. Treating them separately meant each could be solved properly instead of hoping a single clever prompt did both.

System

Two connected pieces. First, structured prompt testing: each use case gets prompts designed, tested against real cases, and refined into a reusable library, so the same task runs the same way regardless of who runs it. Second, an output validation protocol: verified checkpoints an output must pass before it enters a client deliverable, backed by a versioned playbook documenting the rules.

Result

Turnaround time and consistency of deliverables improved by 90%, while the validation layer kept inaccurate outputs out of client work and cut rework. AI shifted from a personal shortcut to a governed, repeatable part of delivery, written down so a colleague could adopt it safely.

Principle

Speed from AI is only an asset once it is checkable. Standardise the input for consistency, validate the output for trust, and never let one depend on the other.

The report that ate Mondays

CASE-02 · REPORTING PIPELINE
Context

A weekly performance report for a US-based client pulled 20+ metrics from five source platforms (paid channels and CRM). The audience was the client's commercial leadership, who needed it reliably every week to steer spend.

Problem

Every Monday, hours went into exporting, reconciling, and reformatting the same numbers by hand. The report was accurate, but the person producing it was the pipeline, and that is a single point of failure.

Approach

The constraint shaped everything: no data warehouse, no engineering support, no budget for tooling. So the rule was build inside the tools already on the desk, and make it inspectable. Separate the work into ingest, clean, and consolidate, then encode the cleaning rules that until then lived only in one head.

System

A Power Query pipeline that ingests each platform export, standardises naming and formats, applies the documented cleaning rules, and lands everything in a single source of truth table feeding the client dashboard. Every transformation step is written down, so a colleague can inspect and run it.

Result

Weekly manual preparation time down over 90%. Reconciliation errors near zero because the rules run identically every week. Monday mornings returned to analysis instead of assembly, and the process survived a full handover test: someone else ran it without me in the room.

Principle

Automation on top of an unexamined process just makes mistakes faster. Map and fix the workflow first, then automate the version that works.

From one-off pulls to a database that grows every week

CASE-03 · DATA QUALITY PIPELINE
Context

A global employee benefits client runs an account-based programme in the US, and its CRM needed senior contacts at target companies: Director level and above, inside a defined profile of company size, revenue band and industry, starting with Manufacturing and Healthcare. In March 2026 there was no data playbook. Contacts came from one-off pulls out of a licensed database, each one costing credits, each one validated by hand, and nothing written down about how the last pull had been done. I was the sole data analyst on the engagement and the person every list ran through.

Problem

Three things fail quietly in a list. Fit: loose industry codes let the wrong companies in, and size labels in the source look like breaches when the underlying data is clean. Deliverability: invalid and trap addresses poison the CRM if they get through. Credits: a duplicate validated twice is money gone. Underneath those sat a structural problem: a single pull is a snapshot of a database that refreshes continuously, so a Monday search on filters the client cared about returned three usable contacts and read as an empty well. Then, midway through the numbered rounds, a different request arrived: a client-supplied list of 9,287 companies needing HR contacts by name, with an estimated cost of 28,000 credits against 1,955 on hand and a deadline five weeks out.

Approach

Build one procedure and make every request a variant of it. Separate the decisions (which profile, which filters, how many credits, who approves) from the mechanics (scope, dedupe, validate, format, deliver), and gate the mechanics so a human confirms the count at every stage. Put a credit gate in front of every export: searching is free, exporting costs, so the exact cost is reported and approved before anything is bought. When the volume exceeds the budget, phase by seniority, VP first, then Director, then Manager, and let each phase earn the next. When the source refreshes faster than a snapshot can catch, stop pulling and run a cycle.

System

Six operational stages, written down and run the same way every time. Intake and integrity: confirm the round, the profile, the row count. Scope and dedupe: US and Canada only, a written rule for blank-country rows based on the person's own location fields, drop every column the CRM does not need, dedupe on email before validation so no address is checked twice. Isolation: the email column alone goes to the validation tool, with a stable record ID kept in the master file. Verdict: results rejoin on email; invalid or trap addresses are excluded, and a record the tool cannot see is excluded, never assumed valid. Format: a fixed 16-column structure mapped to the CRM's property names with a source stamp on every row. Delivery: the client note, the slide copy, the task tickets, the ledger line.

Three motions run on those stages. Numbered rounds opened each scope: seven of them across Manufacturing, Healthcare and their sub-categories, each approved on its own. Weekly cycles keep the scopes growing under a standing approval: count on Monday, let the source accumulate, compile and validate on Friday. List enrichment handled the 9,287-company request as five phases over five weeks, matched to the client's list by company ID, with a per-company coverage tracker answering the question every stakeholder asks: did you cover all of them.

The procedure is packaged as an AI assistant with the rules and stop gates built in. The model only sees the fields a stage needs; the contact name and email columns are dropped before it runs and rejoined after. Every round, workflow, fix and dashboard lives in a versioned data playbook, patched weekly, so a colleague can run the next cycle without me.

Result

As of late September 2026, 21,015 validated contacts delivered: 2,568 from the rounds and weekly cycles, all Director level and above, in the client's CRM; and 18,447 HR contacts across 4,123 companies from the list enrichment, delivered a week ahead of target with about 93% of exported addresses passing validation. The same filters that returned three contacts in a snapshot returned twenty-three by Friday on the first weekly cycle, with no extra credit spend; the latest cycle added 96. A round that took three to four days to validate and format now closes in hours, and every record carries its validation status before it is imported.

Principle

A list is only as good as its worst record, and a process is only as good as its ability to take a request it was not built for. Gate every stage, never let a record default to valid, and write the procedure down so the next request is a variant instead of a rebuild.
