Teaching AI to be checkable

CASE-01 · GENAI DELIVERY WORKFLOWS
Context

Across several US client accounts, I brought Generative AI into my everyday delivery: list building, data cleaning, and persona classification run through Claude, ChatGPT, and Gemini. The work went faster at once; the open question was whether it could be trusted under deadline.

Problem

Faster is worthless if it is wrong. Early prompts were improvised per task, so results varied from run to run, and there was no checkpoint between an AI-generated output and a client deliverable. The risk was quiet: a plausible-looking but incorrect result slipping through unnoticed.

Approach

I framed it as two separate problems. Consistency is an input problem: fix it by standardising the prompts. Correctness is an output problem: fix it with a checkpoint before deployment. Treating them separately meant each could be solved properly instead of hoping a single clever prompt did both.

System

Two connected pieces. First, structured prompt testing: each use case gets prompts designed, tested against real cases, and refined into a reusable library, so the same task runs the same way regardless of who runs it. Second, an output validation protocol: verified checkpoints an output must pass before it enters a client deliverable, backed by a versioned playbook documenting the rules.

Result

Turnaround time and consistency of deliverables improved by 90%, while the validation layer kept inaccurate outputs out of client work and cut rework. AI shifted from a personal shortcut to a governed, repeatable part of delivery, written down so a colleague could adopt it safely.

Principle

Speed from AI is only an asset once it is checkable. Standardise the input for consistency, validate the output for trust, and never let one depend on the other.

The report that ate Mondays

CASE-02 · REPORTING PIPELINE
Context

A weekly performance report for a US-based client pulled 20+ metrics from five source platforms (paid channels and CRM). The audience was the client's commercial leadership, who needed it reliably every week to steer spend.

Problem

Every Monday, hours went into exporting, reconciling, and reformatting the same numbers by hand. The report was accurate, but the person producing it was the pipeline, and that is a single point of failure.

Approach

The constraint shaped everything: no data warehouse, no engineering support, no budget for tooling. So the rule was build inside the tools already on the desk, and make it inspectable. Separate the work into ingest, clean, and consolidate, then encode the cleaning rules that until then lived only in one head.

System

A Power Query pipeline that ingests each platform export, standardises naming and formats, applies the documented cleaning rules, and lands everything in a single source of truth table feeding the client dashboard. Every transformation step is written down, so a colleague can inspect and run it.

Result

Weekly manual preparation time down over 90%. Reconciliation errors near zero because the rules run identically every week. Monday mornings returned to analysis instead of assembly, and the process survived a full handover test: someone else ran it without me in the room.

Principle

Automation on top of an unexamined process just makes mistakes faster. Map and fix the workflow first, then automate the version that works.

The recurring task that became an assistant

CASE-03 · DATA EXPANSION PIPELINE
Context

A global employee benefits client runs an account-based programme in the US and needs its CRM to keep gaining senior contacts at target companies: Director level and above, inside a defined profile of company size, revenue and industry, Manufacturing and Healthcare first. Contacts are sourced from a licensed database that charges credits per export, validated in a separate tool, and uploaded in a fixed CRM format. In March 2026 there was no playbook for any of this. Each pull was a one-off, done by hand, and I was the sole data analyst every list ran through.

Problem

By the third round the shape of the work was obvious: the same export, the same geo and duplicate cleaning, the same validation run, the same 16-column file, the same delivery email and slide. Done by hand it took three to four days per round, most of it mechanical, and every round carried the same quiet risks: a company outside the profile slipping in through a loose industry code, an invalid address reaching the CRM, a duplicate validated twice at a credit each. The work was also about to change shape. Midway through the rounds the client supplied a list of over 9,000 companies and asked for HR contacts at each, a different task with a credit cost far above the balance and a five-week deadline.

Approach

Treat the recurring task as something to write down once and run many times. First I wrote the procedure as a master prompt: the six stages, the rule at each stage, the stop where a human confirms the count before the next stage runs. When the prompt held up across rounds I packaged it as a Claude skill, a file that carries the stages, the profile limits, the validation verdict logic, the file naming, the round ledger and the delivery templates. Then I built a Claude Project around the skill, with the account's rules in its memory, so every run starts from the same place. The judgement stayed with me: which scope, which filters, how many credits, who approves. The mechanics moved into the assistant.

System

A round now runs like this. I drop the export into the Project. The assistant opens it and reports the row count, the columns, the country spread and anything odd, then stops for my confirmation. It then works the stages: scope to US and Canada with a written rule for blank-country rows, drop the columns the CRM does not need, dedupe on email so no address is validated twice, isolate the email column for the validation tool, merge the verdicts back and exclude anything invalid, trapped or unseen, never defaulting a record to valid, and build the 16-column file in the CRM's property names. Every stage ends in a stop, with the counts in front of me. The model only sees the fields a stage needs; the contact name and email columns are dropped before it runs and rejoined after.

The same stages took the new request in their stride. The list enrichment ran as phases by seniority, VP first, with a credit gate before every export (searching is free, exporting costs, so the exact cost is approved first) and a per-company tracker so the client could see coverage against their own list. And when a Monday snapshot of the source returned only three contacts on filters the client cared about, the fix was a weekly cycle: count on Monday, let the source accumulate, compile and validate on Friday, through the same assistant.

At the end of each run the assistant produces the delivery pack: the client email, the slide copy, the task tickets and the ledger line, and offers to build the two deck slides as a file. Every round, cycle and fix is recorded in a versioned data playbook, patched weekly, so the next person can run it without me.

Result

Over 21,000 validated contacts delivered across seven numbered rounds, the weekly cycles that now run on a standing approval, and the 9,000-company list enrichment, which closed a week ahead of its deadline. A round that took three to four days by hand closes in hours, with the same checks applied every time and a status on every record before it is imported. The first weekly cycle turned three contacts from a snapshot into twenty-three by Friday on the same filters, with no extra credit spend. The time came back, and so did the headspace to propose the next thing instead of assembling the last one.

Principle

When the same task arrives a third time, stop doing it and write it down: a prompt, then a skill, then a project. Keep the decisions with a person, give the mechanics to the assistant, and put a stop between every stage so the speed never outruns the checking.
