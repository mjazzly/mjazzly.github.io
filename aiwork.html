Hundreds of spreadsheets with different columns become one table

Replaces: the days spent opening each file, lining its columns up against the template by eye and pasting rows across, with no record of why a column went where it went. Every column lands with its reason logged, nothing is dropped silently, and where a column could mean two fields the run stops and asks.

For: anyone who receives the same report from many branches, teams or suppliers, each in its own layout: finance, operations, a reporting analyst.

Trust
every column with its reason; counts must reconcile
Possible
one table from any number of layouts, each column with its reason
Cost

A folder of spreadsheets in, one clean table and a decision log out. The files should all hold the same data, but each arrives with its own column names and order, a title row here, a totals row there, dates written as text, two columns that mean one. The model reads each file and proposes how its columns map onto the agreed schema, with a reason per column; the code applies the mapping, parses every value against its type, and writes the table. The rules sit in code it cannot skip: three points where it must stop and ask, one where it must decline, and a count that must reconcile or the run fails.

WORK-03 / Data answersDeployed · v1.2

A question in the chat, a number with its definition back

Replaces: the message to an analyst for every number, the query written and checked by hand, and a figure that comes back with no definition attached. Every answer carries its definition and its filters, the same question asked twice gives the same number and says so, and an answer given after new rows arrive says the data changed.

For: the people who message an analyst for a number: a business lead, a manager, anyone who needs a figure they can quote.

Trust
same question, same number; undefined metrics refused
Possible
a number anyone can quote, with its definition attached
Cost
US$0.05 a question; US$0.0014 on the smallest model

Try itask your own question on the smallest model, up to 150 a day across every visitor and 10 from any one; the eight preset questions answer at once from a recorded run

A question about a business table in, a number out. The table holds a year of orders and returns by branch, month, category and channel, and people ask about it all day: returns rate by branch last quarter, which branch grew most, average order value in March. The model chooses which of twelve metrics defined in code answers the question, and which filters and period apply; the code runs the query and returns the number with the metric's definition, the filters applied, the rows it was computed over, the data version and a run id. The model never writes a query and never sees a row. The rules sit in code it cannot skip: a metric nobody has defined is refused with the nearest defined one named, and a period or a branch the data cannot settle stops and asks.

How it runs: a small Node.js tool server on my machine holds the seven tools; the Claude desktop app starts it and calls the tools as it works. The table sits in a DuckDB file on disk with its data version, and every answer is appended to a log with its run id, which is how a repeated question finds the first answer and how a change in the data is noticed. The table is synthetic, written by a seeded generator together with every expected answer, so every expected number is exact and nothing is checked by eye. The public demo runs the same code on Vercel, on the smallest model, and is built only from a green CI (continuous integration) run: every push to the main branch runs the twenty-eight questions through the demo's own code, after the tests with no model, and only a green run moves the branch the demo is built from. A pass that misses is run once more before the run turns red, and a green that needed the rerun opens an issue naming what missed. The same check reruns once a week with no change, and every run's record is kept in the repository.

The table under it: the rows arrive the way an export usually does. A second seeded script writes the table back out untidy: returns as a separate file of events, some logged twice, branches as codes, order times as text, rows the export repeats, and text in mixed case and spacing. A dbt project turns that export back into the table through tested tables, one table for each step from the export to the table the questions read, each built in code and checked by tests before the next is built. Thirty-seven tests check them, from a branch code with no name to order value reconciled against the export, and the rebuilt table must match the table every expected answer came from, byte for byte. They run first in every CI run, before the tests with no model, so a row that fails one turns the run red before any question is asked and the demo does not move.

WORK-04 / Sourced briefTested · v1.3

A weekly brief where every sentence shows where it came from

Replaces: the afternoon spent pulling the brief together by hand, and a page whose sentences cannot be traced afterwards. Every sentence on the released page names the file and the line it came from, and the same week written twice gives the same facts from the same sources.

For: anyone who writes or signs off a weekly status: a programme lead, a team lead, a sponsor who has to stand behind what the page says.

Trust
every sentence names its source; no false fact in ten runs
Possible
a weekly page a sponsor can stand behind, line by line
Cost
US$0.21 a brief; the smallest model misses one case

Six sources in, one page out. Every week someone writes the status brief from the action tracker, the merged table and its log, a few answered questions, two short notes and last week's brief, and afterwards nobody can tell which sentence came from where. Here the model reads the six sources and drafts the page in five fixed sections: what moved, what is due, what changed in the numbers, what needs a decision, open questions. Every sentence carries a claim for each fact in it, meaning each number, name, date, quote and status, with the file and the line or row it came from. The code checks every claim against its source before the page is released; a sentence that fails is taken off the page and listed with the reason. Where two sources disagree, the page shows both. A section with nothing to cite says so. A source marked confidential is declined and named, and a number no source states is never worked out.

WORK-05 / ScorecardTested · v1.2

One command that reruns every build on every model and keeps the score

Replaces: five commands in five folders after every change, and a comparison made by eye. A broken case is named by its build, its model and its case, and the cost of every model on every build sits on one page.

For: the analyst or engineer who maintains the builds and changes a rule or a model, and has to know what it broke and what it now costs.

Trust
a broken case named by build, model and case
Possible
any change checked on every build and every model, in one command
Cost
US$1.75 a sweep on the smallest passing models, US$0.15 the last run in CI

Five builds on this page, each with its own test cases, checker and record. After any change to a skill, a tool server or a model, every one of those case sets has to be run again on every model and compared with the last run, and someone has to decide whether the change broke anything and which model is now the cheapest that passes. Here one command runs every build on every model, each through its own harness and its own checker in a fresh copy, and keeps one scorecard: cases matched, stop gates held, cost, and the change since the last run. It names the smallest model that passes each build. Nothing inside the five builds was rewritten; each gained one small file that says where its pieces are. A run that could have seen its expected answers is refused, kept on the record and never counted.

How it runs: one command on my machine reads the small file in each build, copies each build into a fresh folder, and runs the build's own harness there on each model, two at a time, with Claude reached through the API. Before the model is called, the code scans the copy for the expected answers and refuses the run if any are there; it scans again when the run ends. The words on this page

Every term used on this page, in plain words.

  • Test case. One input with a known right answer. The first two entries have eight each: five ordinary, one it must decline, two that test what it remembers between runs. The third has twenty-eight questions: twenty with exact answers, six it must stop on or refuse, two asked a second time. The fourth has eight weekly briefs: six test weeks, one written twice, one with a new note added. The fifth has nine that test the scorecard itself: a clean sweep, a planted miss in a recorded run, a rule removed from a real skill, a doubled price, an answer file left where the model could read it, a file with a field missing, the same run twice, a new version and a new build. The sixth has one test round of 29 contact rows, each a planted case, with 22 job titles to read and three stop tests. The seventh runs the first entry's eight cases again, on three chat platforms, from one sheet with no code. The eighth runs them in CI on every change, before the change can reach the live service.
  • Claim. One checkable fact in a sentence, such as a number, a name, a date or a quote, paired with the file and the line or row it came from.
  • Expected result. The right answer for a case, written down before the first run, so the run is marked against it and never the other way round.
  • Blind run. A test where the model cannot see the expected answers.
  • Test harness. A script that runs every test case the same way, checks the results against the expected ones, and records the run with its cost.
  • Sweep. One run of every build on every model, started by one command.
  • Regression. A case that passed before and misses after a change.
  • Stop gate. A rule in code that halts the run until a person answers, or declines the task outright.
  • Tool. A function in code the model calls by itself to act. A tool server is the program that holds the tools.
  • Model tier. The size of model, from the largest to the smallest and cheapest. A build that passes on a smaller tier costs less to run.
  • Cache. Context the model has already read, kept so the next call does not pay for reading it again.
  • Version. One numbered state of the rules. A version changes only after a run, and the run that earned it is on the record.
  • Repository. A project's code and its full history, kept on GitHub where anyone can read it, run it, and see how it changed.
